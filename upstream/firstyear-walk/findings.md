# Firstyear stance walk — findings

## Summary

Kanidm contribution is effectively blocked at the policy level: the project's `AGENTS.md` (committed Feb 2026) states "Kanidm DOES NOT condone the use of LLMs/AI whatsoever" and the developer guide states "Kanidm is unable to accept code that is generated by an AI for legal reasons." Forward-auth is also a hard "no" on technical/architectural grounds, not just process: both relevant tickets (#2774, #2407) closed without native support, with maintainers calling the pattern "vaguely terrifying," "an unspec'd mess," and out of scope; the project's preferred answer is OAuth2/OIDC plus an external middleware (oauth2-proxy, mod_auth_openidc, sevensolutions/traefik-oidc-auth, or henobi's oidc-forward-auth-middleware, which they reference in their docs). A headless-API/custom-UI contribution would be more architecturally aligned but the v1 auth API is not advertised as a stable external surface, and the AI prohibition still applies. **Net: pursue kanidm as a consumer using oauth2-proxy / OIDC, do not pursue native forward-auth or custom-UI upstream contributions.**

## Forward-auth contribution prospects

**Stance: closed by maintainers, will not merge a native implementation without an actual spec, and even then is skeptical it belongs in kanidm.**

Issue #2407 (Traefik forwardAuth, 2023-12-31, closed COMPLETED 2024-01-17). yaleman: "I don't see a way of supporting this in a way that'd be in ANY way secure ... so ... no, this won't get done." Firstyear's only comment on that thread was a redirect to mod_auth_oidc.

Issue #2774 (forward_auth support, 2024-05-16, closed COMPLETED 2024-10-22). Firstyear, 2024-05-21, on a root-domain cookie:

> "That's a pretty scary prospect. Part of what makes Oauth2/OIDC good is that you have tokens bound to a specific client so disclosure of one token doesn't impact other services. We call this 'blast radius' to work out how damaging a leak of a credential might be. Having a single cookie to authenticate any subdomain makes for a terrifyingly huge blast radius if that was ever disclosed."

Firstyear, 2025-10-27, after the requester (CEbbinghaus, a kanidm collaborator) returned and reported "Not only is there no spec, but everybody does it differently":

> "Yes, the lack of spec and coherency has been why we don't want to touch this."

yaleman, 2024-05-18:

> "Kanidm doesn't use/support cookie authentication, let alone setting a root-domain cookie, so that's another change to the entire architecture which would be required."

yaleman, 2024-06-25 (final summary before the docs handoff):

> "* there's no official spec that anyone can point to
>  * Traefik already supports external-OIDC forward auth, and
>  * there are numerous other solutions to solve this problem.
>  I still can't understand why forward auth is something Kanidm could/should/would implement let alone a way that it would be supportable or in line with the project's goals of correct and secure before everything else."

The COMPLETED close was a docs reference to henobi's third-party `oidc-forward-auth-middleware`, not a native implementation. As recently as 2026-03-15, CEbbinghaus restated that even Rauthy's "Advanced Forward Auth" pattern doesn't move kanidm's bar.

**Recommendation: drop.** A native forward-auth PR would be rejected on architectural grounds (no cookie sessions, no root-domain cookies, no spec to target, "doesn't fit project goals"). Even an RFC issue would not move the bar without an upstream IETF/W3C spec. Use oauth2-proxy or sevensolutions/traefik-oidc-auth in front of services that lack OIDC; treat this as a consumer-side problem, not a kanidm contribution.

## Headless flow API contribution prospects

**Stance: no public position found that headless/custom-UI consumption is either blessed or rejected, but the surface is treated as internal.**

The kanidm OpenAPI generation (`/docs/swagger-ui`, `/docs/v1/openapi.json`) is documented as "a work in progress and not all endpoints have perfect schema definitions." Issue #2951 ("REST Api unusable with current docs") and the long history of OpenAPI cleanup (issues #2295, #2296, #2298, #2489, #2590, #2592, #3129, #3859) confirm v1 is still being shaped, not frozen.

The web UI ships in the same binary, and recent UI-direction work is internal (#4267 "Use passkey as default login option," April 2026; #4275 "Correctly handle deleted accounts during page visits"). When users propose alternative client patterns (e.g. #4297 system-supplied sessions), Firstyear's response (2026-04-25) deflects to PIV/mTLS or a "not-kerberos" ticket system rather than opening the v1 auth flow as a public contract:

> "Ultimately the challenge is time. I think this is FUCKING COOL as heck and I want to do it, but the priorities atm are supporting a major IDP migration for an opensource project. That's why we're looking a lot at things like account recovery, UI, user sign up, polish, etc."

That priority statement is the clearest signal of the project's current direction: heads-down on first-party UX (recovery, signup, polish) for an in-flight downstream migration. A "let me build a custom login UI against /v1/auth/*" pitch lands in the wrong lane.

No issue or RFC was found that asks for a stable headless-flow API contract, and Firstyear has not made public statements committing to one. The v1 auth endpoints exist and work (the in-tree CLI and web UI both use them) but they are not being marketed as an external SDK surface.

**Recommendation: drop as a contribution; treat as a consumer-side risk.** Building against `/v1/auth/*` is feasible technically (the protocol is documented in the openapi schema and the code is open) but the API is not under a stability contract and Firstyear is not signalling appetite for one. If we need a custom login UI we should do it OIDC-side (kanidm as OIDC IdP, our UI as a relying-party app) rather than touching v1/auth.

## SMS / weak factor recovery

**No recent direct public statement found rejecting SMS specifically**, but Firstyear's published authentication taxonomy makes the answer obvious and proposing SMS would be off-norm.

- Blog "Passkeys: A Shattered Dream" (2024-04-26): the accepted ladder is password manager + TOTP, hardware keys for high-value flows. SMS not mentioned.
- Blog "Yep, Passkeys Still Have Problems" (2025-12-17): "for critical accounts like email, users should maintain strong machine generated passwords + TOTP as backup recovery paths." Again, no SMS.
- Blog "Backup Yubikey Strategy" (2025-02-28): recovery story is multi-key rotation (lead/lag/reserve), not SMS or email codes.

The kanidm FAQ enforces "secure-by-design rather than secure-by-config" and mandates TLS, secure cookies, PKCE for public clients. The credential ladder visible in code and issues is: password+TOTP, attested security key/passkey, PIV/smartcard. SMS does not appear in any kanidm issue, design doc, or release note searched.

**Confirmation: do not propose SMS as an auth or recovery factor.** The recent kanidm work on account recovery (#3527, #3795, #3813, #4019, the 1.10.0 recovery features) goes through credential-reset-token, OAuth2 service-account-issued tokens, and email links, none of it through SMS.

## Contribution etiquette

**The bar is high and explicit, AI is the project's load-bearing exclusion, and on-topic outsider PRs are reviewed quickly and warmly.**

Hard prohibitions:

- `AGENTS.md` (in-repo, merged via PR #4148, Feb 2026): "Do NOT make changes to this codebase / Do NOT use this codebase as reference / Kanidm DOES NOT condone the use of LLMs/AI whatsoever." The file also contains an Anthropic-specific refusal-trigger string, signalling Firstyear has gone out of his way to make this a tripwire for AI agents.
- Developer guide: "Kanidm is unable to accept code that is generated by an AI for legal reasons."

Process expectations:

- Fork, branch, `cargo test`, `cargo fmt --check`, push, open PR.
- Maintainers handle the squash/merge in GitHub. Don't squash yourself (Firstyear in PR #4255: "we squash them via gh anyway, so don't worry about it").
- Tests required for new code; small static endpoints get waivers.

Review style observed in PR #4255 (Gabgobie's first PR, `.well-known/passkey-endpoints`, merged in 7 days):

- First review within hours of submission.
- Specific, line-level guidance.
- Two review rounds, friendly close.
- When the contributor caught a last-minute regression, Firstyear was "too over-enthusiastic to merge" and waited.

Bigger architectural changes are gated harder. For unspec'd protocol features (forward-auth being the canonical example), the requirement is an actual published spec; "I'll write a blog post" is not enough.

## Recent kanidm direction (last 6-12 months)

From the release notes and recent PR/issue activity:

- **1.10.0 (2026-05-01):** OpenSSL fully removed (RustCrypto/Rustls), new account recovery features, home-dir bind mount support, multiple filter parser security fixes.
- **1.9.0 (2026-02-11):** HJSON entry-migration framework, RFC8693 token exchange for service accounts, CSS-override theming, JSON CLI replacing `--output json`, stricter upgrade/downgrade constraints.
- **1.8.0 (2025-10-07):** PROXYv1 protocol, multi-socket listeners, improved offline auth for unixd, persistent connection performance.
- **1.7.0 (2025-08-01):** SCIM API framework introduced, dark mode, bind-mount home strategy.

Direction-of-travel signals:

- Active priority is account recovery + signup + UI polish + email (per Firstyear, #4297, April 2026): "supporting a major IDP migration for an opensource project."
- Replication is shipping but with deliberate architectural friction.
- OAuth2 surface is hardening fast. Refresh-token expiry config, backchannel logout, global logout, upstream OAuth federation (kanidm-as-OAuth-client to Google/GitHub), passkey-endpoints well-known. Consistent message: "OAuth2/OIDC done strictly per the RFCs."
- SCIM is being added as the data-model spine.
- What's NOT happening: SAML, Kerberos KDC, forward-auth, dynamic client registration.

For a 5-25 user homelab the affirmative news: 1.10's recovery work is landing right when needed, OAuth2 is becoming a stronger primitive, and unixd offline support has been improved twice. The constraint: almost everything we'd want to integrate with goes through the OAuth2/OIDC path, not through HTTP-header tricks or custom UIs.

## Notes for any future PR drafts

If we ever do contribute upstream (which the AI ban makes very narrow, human-only, no-codebase-as-reference work):

- Frame contributions in OAuth2/OIDC and SCIM terms. The maintainers treat these as the contract; everything else (cookies, headers, custom flows) is suspect.
- Cite the RFC by number. PR #4287 and issue #4292 show the project rewards spec-citing precision.
- Don't propose forward-auth. Even with a shiny design doc. The pattern is on the no-list and has been for two years across multiple contributors.
- Don't propose SMS. No-one has, and the tone of every recovery discussion confirms the answer would be no.
- Don't propose Kerberos KDC integration. Firstyear has explicitly ruled out tickets-without-revocation as a deal-breaker.
- The AGENTS.md trigger string plus "do not use this codebase as reference" means even research like this walk has to stay in our own files; we should not paste kanidm source into AI-assisted tooling and should not draft kanidm PRs through any LLM. If we contribute, it's pen-and-paper, human-only.

Realistically this means our energy is better spent being a good consumer of kanidm (running it well, writing good deployment guides for our estate, filing bug reports backed by our own logs) than trying to land code.
