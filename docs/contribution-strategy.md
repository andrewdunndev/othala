# Contribution strategy

How dunn.dev/auth relates to the upstream kanidm project. The original posture was upstream-first; Phase 0 research changed that.

## Current posture: consumer-only

dunn.dev/auth does not contribute to kanidm upstream. The Phase 0 research walk (see `../upstream/firstyear-walk/findings.md`) surfaced three blockers that close off contribution as a viable path:

1. **AI/LLM ban.** Kanidm's `AGENTS.md` (merged Feb 2026) states "Kanidm DOES NOT condone the use of LLMs/AI whatsoever" and the developer guide adds "Kanidm is unable to accept code that is generated by an AI for legal reasons." The dunn.dev workflow uses AI assistance heavily across the estate. Pen-and-paper human-only contribution to kanidm is theoretically possible but realistically out-of-scope for a homelab side project.
2. **Forward-auth is rejected on architectural grounds.** Two issues (#2407, #2774) closed by maintainers Firstyear and yaleman with strong reasoning around blast radius and lack of an authoritative spec. The maintainers redirect users to oauth2-proxy / mod_auth_openidc / sevensolutions/traefik-oidc-auth / espresso-lab/oidc-forward-auth-middleware / Rauthy.
3. **Browser BYO-UI is closed.** PR #2980 closed 2026-04-30 with maintainer position: custom UIs must be a subdomain of the IDM. Three structural blockers in kanidm (no CORS, single-host bearer cookie, WebAuthn RP-id binding) make a custom Astro login form on a different domain technically not viable.

We are pure consumers. Patterns we develop — CSS skins for the kanidm HTMX login UI, custom Caddy image with caddy-security, kanidm CLI configuration scripts, home-portal OIDC RP design — are documented independently in this repo. We do not propose them upstream.

## What this is not

This is not a fork strategy. We are not maintaining a private kanidm patch series. We run upstream kanidm releases unmodified. If a future need arises that genuinely requires patching kanidm, that triggers a re-evaluation of the substrate, not a fork.

## Bug reports and operational engagement

We can still file bug reports and operational questions upstream when we have something to contribute that doesn't require code generated through AI assistance:

- Concrete deployment-derived bug reports (logs, repro steps, observed behavior)
- Documentation issues we encounter
- Real-world deployment notes that may help other operators

These are written by hand and small enough to be safely human-only artifacts. They are not the load-bearing path; running kanidm well in our own estate is.

## What "grave" looks like

The bar for abandoning kanidm and revisiting Ory remains:

- **Project abandonment.** Maintainer disappears, no successor, security advisories unaddressed for >90 days.
- **Fundamental UX failure.** Phone test reveals passkey UX is unworkable for the family even after our customizations, with no upstream path to fix.
- **Architectural mismatch.** Some property we haven't thought of (replication, scaling, integration) makes kanidm unable to grow with the estate over the next 5+ years.

Phase 0 findings did not hit this bar. Findings adjusted scope (no contributions, no Layer 2 custom login) but did not invalidate the substrate decision. The "stay-with-kanidm" bias is strong; Ory remains wrong-shaped for the homelab use case.

## Historical context

The original framing of this strategy (drafted before Phase 0 research) imagined a contribution arc parallel to the existing bootc work: forward-auth endpoint + headless flow API as upstream targets, with documented-independently as the fallback if upstream rejected. Research collapsed both targets directly into the fallback before any code was drafted.

The bootc contribution arc remains intact for that project. Kanidm is a different shape with a different maintainer posture, and the consumer-only outcome here doesn't generalize.
