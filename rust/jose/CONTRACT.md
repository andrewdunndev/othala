# jose contract

The public surface is the generated `public-api.txt`. Item tags (`jose-NN`) name the queue item that landed a claim; `git log --grep` finds it. Each claim carries one tag from the claims ledger: *Type* (the program does not compile), *Runtime* (a check returns an error or a value), *Obligation* (the consumer's or host's, which the crate cannot see). Non-goals and non-claims follow; each non-goal names the claim that holds it.

Checks:
- `ui:x (Ennnn)` is `tests/ui/fail/x.rs` with its committed `.stderr` opening with that rustc code, and its compiling twin `tests/ui/pass/x.rs` one line and one token away (`just twins`). `tests/ledger.rs` fails unless the cases on disk are exactly the names below; `ui:x (Ennnn, jose-NN)` lands with that item, since its case calls a function that item writes. `off_*` cases run with every feature off, the rest with every feature on.
- `api:<Item>` is an item path the committed `public-api.txt` declares (`Type::method`, or a bare top-level name; impl and attr lines declare none) and `api-absent:<Item>` one it does not declare (a bare name matches no path's last segment; `Type::b` needs `Type` declared); the snapshot is under `just api`. An absent accessor or constructor is an `api-absent:` ref; an absent impl is held by the snapshot (`just api`) and its `ui:` case.
- `vec:f#id` is a case of `rust/vectors/f`; `vec:f` is the whole file. A refusal's error kind is always compared: the file names it, and for a pinned external file the row test holds it by vector id. Rows read files through testkit's typed readers (`testkit::vectors::{wycheproof, sections, figures}`), which check each file's SHA-256 and count against `SOURCES.toml`.
- `row:x` is `tests/row_x.rs`, one file per family. `lib:m::x` is a row run as a `--lib` filter over a `#[cfg(test)]` module of `src/m.rs`, where the inputs are raw primitive values no public item takes (ruling R-l). `prop:t` is a fixed-seed proptest in a row file; `unit:m::t` a test in `src/m.rs`.
- `gate:x` is `just x` with jose's `gates.json`.
- `spec:rfcN` is every requirement sentence of the pinned RFC (`rust/spec/rfcN.json`, `just spec-extract`) mapped by a `//=` citation in this crate: an implementation under `src/` and a test above a `#[test]` fn, an exception with its reason, or a counted todo; `spec:rfcN#s` is section s mapped with no todo. The citation quotes the sentence, so a claim here names the section and never restates it. Scope: a requirement sentence is one holding MUST, MUST NOT, REQUIRED, SHALL or SHALL NOT in capitals (`spec/extract.mjs`); a sentence holding only SHOULD, SHOULD NOT or RECOMMENDED is out of scope and unmapped: 9 in RFC 7515, 1 in RFC 7516, 10 in RFC 7517, 10 in RFC 7518, 9 in RFC 7519.
- `fuzz:t` is the cargo-fuzz target `fuzz/fuzz_targets/t.rs` (`just fuzz`) with its committed `fuzz/corpus/t` replayed by `tests/fuzz_corpus.rs`, each seed's outcome named in its file name.

## Type
- T1 A parsed `Jws` has no payload accessor; the payload exists only as the `Payload` that a verify returns: api-absent:Jws::payload api:Jws::verify.
- T2 A parsed `Jwt` has no claims or payload accessor, and a `VerifiedJwt` none either, so `claims` with a `Policy` is the only way out (RFC 8725 3.8, 3.9, 3.11): api-absent:Jwt::claims api-absent:Jwt::payload api-absent:VerifiedJwt::payload api:VerifiedJwt::claims.
- T3 `Payload`, `VerifiedJwt` and `Plaintext` have no public constructor or field: api-absent:Payload::new api-absent:Payload::0 api-absent:VerifiedJwt::new api-absent:VerifiedJwt::0 api-absent:Plaintext::new api-absent:Plaintext::0.
- T4 `Policy` has no `Default`: ui:policy_default (E0277).
- T5 Issuer and audience are distinct types, so they cannot be swapped into a policy (8725 3.8, 3.9): ui:policy_swap (E0308).
- T6 A policy is typed by its kind, so an ID-token policy is not an access-token policy (8725 3.11, 3.12): ui:kind_policy (E0308).
- T7 Only a `ReadBack` kind has `Policy::read_back`, the one policy that skips the audience and the one that takes `Expiry::Unchecked`; every `Policy::new` requires `exp`: ui:read_back_kind (E0599).
- T8 A verify key verifies only its own algorithm, and `Jws::verify::<A>` takes only a `VerifyKey<A>` (8725 3.1): ui:alg_bound (E0308).
- T9 Issuing is typed like verifying: `Header<A>` and `Unsigned<A>` carry the algorithm in the type, so a header cannot name one algorithm while another signs: ui:unsigned_alg_bound (E0308).
- T10 A `Signer<A>` returns `A::Signature`: a fixed-size array for HS, ES and EdDSA, so `finish` and `sign` cannot receive a signature of the wrong length for those: api:Signer api:Alg::Signature.
- T11 An HMAC key cannot come from a public JWK: `Jwk::verify_key` takes only `PublicAlg`, which no HS marker implements, closing the RS-to-HS swap on the static path (8725 3.1): ui:hmac_public_jwk (E0277).
- T12 `none` is not a `SigningAlg`, so no header the crate issues carries it (8725 3.2, RFC 7518 3.6): ui:no_none_alg (E0599).
- T13 A decrypt key decrypts only under its own key-management algorithm: ui:decrypt_key_bound (E0308).
- T14 `EncryptKey` and `DecryptKey` take only a key-management algorithm, so no JWS algorithm (EdDSA among them) is a JWE key's: ui:jws_alg_jwe_key (E0277).
- T15 This crate's own RSA private key never signs through `Signer`, which takes no entropy: `SigningKey<Rs*>` and `SigningKey<Ps*>` are not `Signer`s and sign only through `sign_blinded`; with `rsa-sign` off no RS or PS `SigningKey` exists and `BlindedAlg` does not exist. A host's own `Signer<Rs256>` (WebCrypto, a KMS) is allowed: ui:rsa_signer (E0277), ui:off_rsa_sign (E0405).
- T16 `SecretJwk`, `SigningKey`, `DecryptKey` and `Plaintext` are not `Serialize`, so private key material and plaintext cannot become a store record or a log field: ui:secret_jwk_serialize (E0277), ui:signing_key_serialize (E0277), ui:decrypt_key_serialize (E0277), ui:plaintext_serialize (E0277).
- T17 `SecretJwk`, `Plaintext` and `VerifyKey` are not `Clone`: ui:secret_jwk_clone (E0277), ui:plaintext_clone (E0277), ui:verify_key_clone (E0277); nor are `SigningKey`, `AnyVerifyKey`, `AnySigningKey`, `EncryptKey` and `DecryptKey`: api:SigningKey api:AnyVerifyKey api:AnySigningKey api:EncryptKey api:DecryptKey.
- T18 `Compact` is a bearer value with no equality and no `Display`: ui:compact_eq (E0277), api:Compact.
- T19 `Alg`, `KeyAlg` and `Enc` are sealed, and through them every marker trait, so a consumer cannot add an algorithm the contract did not review: ui:sealed_alg (E0277), ui:sealed_key_alg (E0277), ui:sealed_enc (E0277). `Signer`, `TokenKind` and `ReadBack` are open on purpose (an HSM, a token kind).
- T20 Every public enum is `#[non_exhaustive]`: ui:error_kind_exhaustive (E0004), `just api`.
- T21 No function fetches: nothing takes a URL, a socket or a file, and `jku`, `x5u`, `x5c` and header `jwk` have no accessor (8725 3.10): api-absent:jku api-absent:x5u api-absent:x5c api-absent:Header::jwk, gate:lint (sockets and files are `disallowed_methods`).
- T22 With `es512` off `Es512` does not exist, and with `rsa-decrypt` off neither do `RsaOaep` and `RsaOaep256`: ui:off_es512 (E0425), ui:off_rsa_decrypt (E0425).
- T23 jose is stateless: no signature names `Effect`, `Pending`, `Store`, `Row` or `Receipt`, so it adds no transaction domain: api-absent:Effect api-absent:Pending api-absent:Store api-absent:Row api-absent:Receipt.
- T24 Time enters only as a `UnixTime` argument and randomness only as `&mut impl Entropy`; no verify and no `decrypt` takes entropy: `just api`, gate:lint (clock and OS randomness are `disallowed_methods`).
- T25 `no_std` plus `alloc` for wasm32-unknown-unknown and thumbv7em-none-eabi, with no features and with every feature: gate:wasm, gate:thumb.
- T26 MSRV 1.89 against the committed lock: gate:msrv.
- T27 The direct runtime dependencies are `deps.txt`'s (base, serde, serde_json without `arbitrary_precision` or `preserve_order`, sha2, hmac, p256, p384, ecdsa, ed25519-dalek, rsa, aes, aes-gcm, cbc, aes-kw, one-step-kdf; `es512` adds p521, `rsa-decrypt` sha1 and rand_core, `rsa-sign` rand_core); curve crates without `std`; the `Entropy`-to-`rand_core` adapter rsa needs is private to jose: gate:deps, gate:deny.
- T28 Three features, all off by default: `es512`, `rsa-decrypt`, `rsa-sign`; every other algorithm is always built: `Cargo.toml`, gate:test with every feature and with none (R-i).
- T29 The modules sit in the layers `layers.json` lists and import only from their own layer or below, so no import cycle exists between modules (`alg` does not reach JWE internals, `key` does not reach `jwk`): gate:layers.

## Runtime: JWS
- R1 RFC 7515 A.1 (HS256), A.2 (RS256) and A.3 (ES256) verify under their keys, and each tampered, truncated or signature-less case is refused: vec:rfc7515/jws.json, row:rfc7515.
- R2 RFC 7515 A.4 (ES512, `es512`), A.6 (general) and A.7 (flattened) verify; A.5 (unsecured) is refused under every key: vec:rfc7515/appendix-a4-a7.json, row:rfc7515_json (A.4 in row:es512).
- R3 RFC 7520 4.1 (RS256), 4.2 (PS384), 4.3 (ES512, `es512`), 4.4 (HS256), 4.6, 4.7 and 4.8 verify in each serialization given; 4.5 (detached) is refused: vec:rfc7520/jws.json, row:rfc7520_jws (4.3 in row:es512).
- R4 The header `alg` is compared with the key's, byte for byte, and never selects code: any other value is `AlgMismatch`, `none`, a case variant and an HS value over a public key included (8725 3.1): vec:jose-derived/header.json#alg-none-with-mac, #alg-case-differs, vec:rfc8725-derived/jws-alg.json, vec:rfc7515/jws.json#alg-none-unsigned, #alg-confusion-rs256-as-hs256, row:rfc8725.
- R5 A missing or non-string `alg` is refused (`Malformed`): vec:jose-derived/header.json#alg-missing, #alg-not-string.
- R6 Wycheproof signatures through `VerifyKey::verify_signature`: every `valid` case verifies and every `invalid` case is refused; `acceptable` cases and HMAC keys shorter than the hash (R13) are not applicable by name: vec:wycheproof/hmac_sha{256,384,512}_test.json (row:wycheproof_hmac), ecdsa_secp{256r1_sha256,384r1_sha384}_p1363_test.json (row:wycheproof_ecdsa) and, under `es512`, ecdsa_secp521r1_sha512_p1363_test.json (row:es512), ed25519_test.json (row:wycheproof_eddsa), the nine `rsa_signature_*` files (row:wycheproof_rsa), the six `rsa_pss_*` files (row:wycheproof_pss).
- R7 ECDSA signatures are only the RFC 7518 3.4 `R || S` form: every case of the ASN.1 DER files is refused, valid ones included: vec:wycheproof/ecdsa_secp256r1_sha256_test.json, ecdsa_secp384r1_sha384_test.json, ecdsa_secp521r1_sha512_test.json (`es512`, row:es512), row:wycheproof_ecdsa; spec:rfc7518#3.4.
- R8 EdDSA verifies with ed25519-dalek's `verify_strict`: a small-order key or a non-canonical `R` or `S` is refused: vec:wycheproof/ed25519_test.json, row:wycheproof_eddsa.
- R9 A member named twice in a header, at any depth and through any escape (`alg`), or in more than one of a token's headers, is `DuplicateMember`; names compare after decoding, so an escaped surrogate pair and the literal character outside the BMP are one name, and a lone surrogate escape is `Malformed` (R12) (spec:rfc7515#4, spec:rfc7515#5.2); the crate's own pre-scan finds it, since serde's struct reading sees only known members: vec:jose-derived/header.json#dup-alg-different, #dup-alg-same, #dup-typ, #dup-escaped-name, row:rfc8725; spec:rfc7516#4.
- R10 A `crit` header member is `CriticalHeader` when it names an extension (none is understood), and is refused when empty, not an array (`null` included), naming a registered header or naming an absent one (spec:rfc7515#4.1.11): vec:jose-derived/header.json#crit-unknown, #crit-empty, #crit-not-array, #crit-null, #crit-registered-name, #crit-name-absent.
- R11 RFC 7797 is not implemented: a `b64` header member is refused, with or without `crit`, and `null` is a member, not an absent one: vec:jose-derived/header.json#b64-false-crit, #b64-false-no-crit, #b64-null.
- R12 A header that is not a UTF-8 JSON object, a segment that is not canonical unpadded base64url (base's codec), whitespace, or other than three segments is `Malformed`; an unknown member is ignored: vec:jose-derived/header.json#header-array, #header-not-json, #segment-padded, #whitespace-inside, #two-segments, #four-segments, #unknown-member-ignored, #control-valid.
- R13 An HMAC key shorter than its hash output is `WeakKey` (RFC 7518 3.2, 8725 3.5): vec:jose-derived/keys.json#hs256-32-bytes, #hs256-31-bytes, #hs384-47-bytes, #hs512-63-bytes, row:keys.
- R14 A string `kid` never chooses or refuses: a valid signature verifies under its key whatever `kid` says, and a header `jwk`, `jku`, `x5u` or `x5c` never changes an outcome (8725 3.10): `Jws::kids` lists them as hints only: prop:kid_never_selects in row:rfc8725.
- R15 A general JWS verifies when a signature whose `alg` is the key's verifies; when such signatures exist and none verifies it is `BadSignature`, when none names the key's `alg` it is `AlgMismatch`; more than `MAX_ENTRIES` signatures is `TooLarge`; a signature whose `alg` needs an off feature is skipped as not the key's `alg` among several, and is `UnsupportedAlg` in a compact or single-signature token: vec:rfc7520/jws.json (4.8), vec:rfc7515/appendix-a4-a7.json (A.6), row:rfc7520_jws; oracle gap: no vector carries the skip among several, requested of the oracle lane.

## Runtime: keys, JWK and JWK Set
- R16 Key type and curve bind the algorithm, and this is the whole table: EC P-256 takes only ES256 and ECDH-ES*, P-384 only ES384 and ECDH-ES*, P-521 only ES512 and ECDH-ES* (`es512`), RSA only RS*, PS* and RSA-OAEP* (`rsa-decrypt`), OKP Ed25519 only EdDSA, `oct` only HS*, A*KW, A*GCMKW and `dir`. Any other pairing is refused, in one order: decode refuses first, whatever the algorithm: an unknown or uncompiled curve is `UnsupportedAlg` (R17, R50), which covers P-521 with `es512` off (the vector carries it as `expect.kind_without_es512`), and a non-`oct` key given to `SecretJwk::decode` is `Malformed` (#hs256-rsa-key); only a key that decodes reaches binding, and there every pairing outside the table is `AlgMismatch`: vec:jose-derived/keys.json#es256-p256, #es256-p384-key, #es256-p521-key, #es384-p256-key, #es256-rsa-key, #es256-okp-key, #rs256-ec-key, #hs256-rsa-key, #eddsa-ed25519, row:keys.
- R17 X25519, X448 and Ed448 keys are `UnsupportedAlg` (R-e), as a JWK, as an `epk` and inside a set (skipped there): vec:jose-derived/keys.json#eddsa-x25519-key, vec:jose-derived/jwe-header.json#x25519-ecdh-es-a128kw, vec:rfc8037/appendix-a.json (A.6, A.7), row:rfc8037.
- R18 An EC point off its curve, the identity, a coordinate shorter than the curve's full length or a missing member is `Malformed` at decode, for keys and a JWE `epk` alike (8725 3.4; RFC 7518 6.2.1.2, 6.2.1.3): vec:jose-derived/keys.json#es256-off-curve, #es256-point-zero, #es256-x-short, #es256-crv-missing, #es256-y-missing; spec:rfc7518#6.2.1 spec:rfc7518#6.2.1.2 spec:rfc7518#6.2.1.3 spec:rfc7518#6.2.2 spec:rfc7518#6.2.2.1.
- R19 An RSA modulus below `MIN_RSA_BITS` is `WeakKey` and above `MAX_RSA_BITS` `TooLarge`; `e` above `MAX_RSA_EXPONENT` is `TooLarge`, and `n` and `e` must be minimal Base64urlUInt (RFC 7518 2): vec:jose-derived/keys.json#rs256-2048, #rs256-2047, #rs256-1024; spec:rfc7518#2 spec:rfc7518#3.3 spec:rfc7518#3.5 spec:rfc7518#4.3 spec:rfc7518#6.3.1 spec:rfc7518#6.3.1.2 spec:rfc7518#6.3.2 spec:rfc7518#6.3.2.7.
- R20 A JWK's `alg`, when present, must equal the requested algorithm (`AlgMismatch`); `use` and a non-empty `key_ops` must permit the operation, else `KeyUse` (RFC 7517 4.2, 4.3); a `use` that disagrees with `key_ops`, an unknown `key_ops` value and a repeated one (4.3: MUST NOT) are `KeyUse`. Each JWE algorithm needs its own operation, read from the wording of 4.3: `dir` `encrypt` or `decrypt` (the content), a key-wrapping algorithm (`A*KW`, `A*GCMKW`, `RSA-OAEP*`) `wrapKey` or `unwrapKey` (a key), key agreement (`ECDH-ES*`) `deriveKey` or `deriveBits`; `use: enc` permits all of them; `ECDH-ES*` also takes `deriveBits`, a deliberate relaxation of 4.3's wording ("not to be used as a key") because WebCrypto-exported ECDH keys carry it: vec:jose-derived/keys.json#hs256-use-enc, #hs256-key-ops-encrypt, #hs256-use-key-ops-disagree, #hs256-key-ops-duplicate, #a256kw-key-ops-wrap-key, #a256kw-key-ops-unwrap-key, #kw-key-ops-derive-only, #a256kw-key-ops-encrypt, #a256kw-key-ops-wrap-key-only, #a256gcmkw-key-ops-encrypt, #dir-key-ops-encrypt, #dir-key-ops-wrap-key, #kw-key-ops-sign-only, unit:jwk::decode::key_ops_serve_one_operation_per_algorithm; spec:rfc7517#4.3.
- R21 `AnyVerifyKey::from_jwk` refuses a JWK without `alg` (`KeyAlgMissing`), an `alg` its key type cannot take (R16), and an `enc`-only key (`KeyUse`); a `Jwk` is never `oct`, so the `oct` cases of keys.json (#any-alg-bound, #any-alg-missing, #any-enc-key) run through `AnySigningKey::from_jwk` on a `SecretJwk`, which binds the same way; `from_jwk_for` binds the algorithm the host expects and refuses a JWK `alg` that differs (`AlgMismatch`); `verify_any` compares the header `alg` with the key's and never selects by it: vec:jose-derived/keys.json#any-alg-bound, #any-alg-missing, #any-enc-key, #any-alg-kty-mismatch, row:keys.
- R22 `AnySigningKey::from_jwk` binds the JWK's `alg` (`KeyAlgMissing` without one) and refuses an RS or PS key (`UnsupportedAlg`; it signs through `sign_blinded`); as a `Signer<A>` it is `AlgMismatch` unless `A` is its algorithm: unit:jwk::any::sign_binds.
- R23 RFC 7520 section 3 keys decode: 3.1 as `Jwk` and 3.2 as `SecretJwk` (both P-521, so under `es512`; `UnsupportedAlg` with it off, R50), 3.3 as `Jwk`, 3.4 as `SecretJwk`, 3.5 and 3.6 as `oct` `SecretJwk`; a private member or `kty: oct` given to `Jwk::decode` is `Malformed`: vec:rfc7520/jwk.json, row:rfc7520_jwk (3.1 and 3.2 in row:es512).
- R24 RFC 8037 A.1 and A.2 keys decode, A.3's thumbprint matches, A.4's JWS is reproduced byte for byte by `Unsigned::<EdDsa>::jws(Header::new(), ..).sign(..)`, and A.5 verifies: vec:rfc8037/appendix-a.json, row:rfc8037.
- R25 Thumbprints (RFC 7638 3) cover the required members only, for public, private and `oct` keys alike, so member order, whitespace, private and optional members never change one; a JWK missing a required member or of an unknown `kty` has none (`Malformed`, `UnsupportedAlg`): vec:rfc7638/thumbprint.json, vec:jose-derived/thumbprint.json, row:rfc7638.
- R26 `JwkSet::decode` skips, and does not count, a member object that is not a key it supports, whatever the reason: an unknown `kty`, X25519, a missing or ill-formed member, a `use`, `key_ops` or `alg` value it does not know, a weak modulus (RFC 7517 5: SHOULD ignore). It refuses, as a whole, a document without a `keys` array or a `keys` member that is not an array (`Malformed`), an array member that is not an object (`Malformed`), a member named twice at any depth (`DuplicateMember`), and more than `MAX_JWKS_KEYS` kept keys (`TooLarge`; a parse bound, counted before the shared-`kid` removal). Members that share a `kid` are skipped too (R27): vec:jose-derived/jwks.json#two-keys, #unknown-kty-skipped, #member-missing-y-skipped, #unknown-use-skipped, #unknown-key-ops-skipped, #key-ops-duplicate-skipped, #keys-missing, #keys-not-array, #member-not-object, #dup-keys-member, #dup-kid-skipped, unit:jwk::set::members_that_are_not_supported_keys_are_skipped, unit:jwk::set::members_that_share_a_kid_are_all_skipped, unit:jwk::set::a_set_malformed_as_a_whole_is_refused, row:keys; spec:rfc7517#2.
- R26b `JwkSet::decode_public` is `decode` for a document fetched from a remote `jwks_uri`: a key carrying any private parameter (`d`, `p`, `q`, `dp`, `dq`, `qi`), and any `oct` key, is dropped whole and not counted so only asymmetric public keys can come out of it; a document the host trusts (its own) goes through `decode`: unit:jwk::set::remote_sets_keep_asymmetric_public_keys_only; oracle gap: no vector family carries a mixed remote set, requested of the oracle lane.
- R27 `JwkSet::find` matches `kid` byte for byte and returns the key or `None`: an unknown `kid` is the host's cue to fetch the set again (OpenID Connect Core 10.1.1), not an error, and no key can verify for it. House rule, stricter than RFC 7517 4.5's example of equal `kid`s as equivalent alternatives across key types: `JwkSet::decode` skips every member whose `kid` another member shares, since a lookup could not choose between them, and keeps the rest; a set left with none is empty, as when every member is skipped for any other reason. `JwkSet::new`, given the host's own keys, refuses a repeated `kid` (`DuplicateMember`): a repeat there is a host bug, while a remote set is not ours to refuse. So a match is never a pick: vec:jose-derived/jwks.json#find-by-kid, #find-absent-kid, #dup-kid-skipped, unit:jwk::set::find_is_some_for_a_kid_the_set_holds_and_none_otherwise, row:keys.
- R28 A member named twice anywhere in a JWK, a JWK Set or a JWE `epk` is `DuplicateMember`, found by the crate's pre-scan: vec:jose-derived/jwks.json#dup-keys-member. A JWK's public members (`kty`, `crv`, `x`, `y`, `n`, `e`) may be written with JSON escapes; a secret member (`d`, `p`, `q`, `dp`, `dq`, `qi`, `k`) with one is `Malformed`, so no unwiped copy of it is made, and `oth` that is not an array is `Malformed`: vec:jose-derived/keys.json#es256-escaped-members, unit:jwk::decode::escaped_and_null_members.
- R29 `Kid`, `Issuer` and `Audience` refuse empty text (`Malformed`) and more than `MAX_NAME_LEN` bytes (`TooLarge`); their `Deserialize` goes through the same constructor, so a stored record cannot hold one the constructor refuses; `Kid::from_thumbprint` is the thumbprint's 43-character base64url text: unit:jwk::decode::kid_bounds, unit:claims::name_bounds.
- R30 `Serialize` on `Jwk` writes `kty`, `crv` and the public members, then `kid`, `alg`, `use` and `key_ops` when present, and nothing else; `JwkSet` writes `{"keys": [...]}` of its public keys only, in order; decoding what either writes gives the same keys; `SecretJwk::public` keeps `kid`, `alg` and `use`: prop:jwk_round_trip in row:keys.

## Runtime: JWT claims
- R31 `iss` must equal the policy's issuer (`Issuer`) and be present (`MissingClaim`) (8725 3.8): vec:jose-derived/claims.json#iss-wrong, #iss-missing, row:claims.
- R32 `aud`, a string or an array of strings, must contain the policy's audience (`Audience`) and be present (`MissingClaim`) (8725 3.9); under `Policy::read_back` it must be present and well typed and is not compared, a deviation from RFC 7519 4.1.3 for a token the verifier issued itself (an `id_token_hint` names its client, not the issuer), so the consumer checks that the `aud` it reads names a client it issued to (O9): unit:claims::read_back_policy, vec:jose-derived/claims.json#aud-wrong, #aud-array-without, #aud-missing, #aud-array-contains, row:claims.
- R33 `typ` is read from the protected header and compared case-insensitively with an `application/` prefix removed; `Typ::Explicit` requires it equal (`Type`, absent included); `Typ::Generic` accepts it absent or equal to `JWT` and refuses any other (8725 3.11, 3.12): vec:jose-derived/claims.json#typ-wrong, #typ-missing, #typ-application-prefix, row:claims.

## Obligation
- O1 The `Entropy` given to `encrypt`, `decrypt_blinded` and `sign_blinded` never repeats a draw, since a repeated GCM IV under one key loses confidentiality and integrity: the host's.
- O2 The key a consumer verifies with belongs to the issuer its `Policy` names (8725 3.8): the consumer's; `oidc-provider` states it for client assertions and `id_token_hint`.
- O3 Kinds under `Typ::Generic` stay apart by issuer, audience and required claims (8725 3.12): each kind's author.
- O4 A token's single use (`jti` of a client assertion, a logout token) is the consumer's: it guards a `Digest` of the `jti` in its own `base::Effect`; jose holds no rows (T23).
- O5 Private key JWK text lives in host secrets, never in a store row; keys are generated outside the crate (N12) and enter only as JWK text or raw `oct` bytes: the host's; T16 makes a store record of one a compile error; spec:rfc7517#9.2.
- O6 A `dir` or A*GCMKW key used with random 96-bit IVs is limited to 2^32 messages (NIST SP 800-38D 8.3), and rotating it is the host's; spec:rfc7518#8.4.
- O7 One key, one purpose: a host that must keep signing and key agreement apart on one EC key, or HMAC and key wrap on one `oct` key, publishes `use` or `key_ops` (R20).
- O8 An HMAC or `oct` key carries the entropy its length implies: the host's, since R13 checks only the length.
- O9 A `ReadBack` kind is implemented only for tokens the verifier itself issued, and read back only under its own key (O2), and its consumer checks that the `aud` read back names a client it issued to (R32): the kind's author.
- O10 `rsa-sign` and `rsa-decrypt` are enabled only where an RSA private key is required, accepting the Marvin residual risk (NC2): the host's.
- O11 HS keys, `oct` JWK material and content-encryption keys are `base::SecretBytes`, never jose-owned buffers, and are read (`expose`) only in `src/sig/hmac.rs`, `src/jwk/decode.rs` (decoding into the curve and rsa types), `src/jwk/thumbprint.rs` (an `oct` key's `k`), `src/jwe/envelope.rs` (a `Plaintext`'s bytes), `src/jwe/kw.rs`, `src/jwe/content.rs`, `src/jwe/ecdh.rs` and `src/jwe/oaep.rs`; private EC, Ed25519 and RSA keys live in their crates' own types, so `src/sig/{ecdsa,ecdsa_p521,eddsa,rsa_sign}.rs` read none. Held by gate:lint, gate:canary and gate:own under ruling R-j once base-expose lands: jose then enables `base/expose` and declares these modules as `expose` in `gates.json` (a dependency of the first item that calls `expose`, jose-07).
- O12 A key set fetched from a remote `jwks_uri` is decoded with `JwkSet::decode_public`, never `decode` (R26b): the host's, and every consumer's, `oidc-provider` among them.

## Non-goal
- N1 Unsecured JWS (`alg: none`): T12, R2, R4; spec:rfc7518#3.6.
- N2 RSA1_5 key encryption (RFC 7516 11.4, 11.5 downgrade and timing oracle): no `JweAlg` variant, R48, R49, R51; spec:rfc7518#4.2.
- N3 PBES2 (attacker-chosen `p2c`): no variant, R49, R51; spec:rfc7518#4.8 spec:rfc7518#4.8.1.2.
- N4 JWE compression (`zip`, 8725 3.6): R49, R51.
- N5 X25519 and X448 (ECDH-ES over OKP) and Ed448 (R-e): R17.
- N6 RFC 7797 unencoded payload: R11.
- N7 Detached content (RFC 7515 F): R3.
- N8 Key fetching (`jku`, `x5u`, JWKS refresh) and header-embedded keys (`jwk`, `x5c`): T21, R14.
- N9 X.509 in a JWK (`x5c`, `x5t`, `x5t#S256`, `x5u`): ignored at decode and never written: R30; spec:rfc7517#4.6 spec:rfc7517#4.7 spec:rfc7517#4.8 spec:rfc7517#4.9.
- N10 Producing a multi-recipient JWE, and a JWE key chosen at runtime by the JWK's `alg`: `just api`; parsing and decrypting a general JWE is R52.
- N11 Claims from an encrypted-only JWT: `Plaintext` has no claims path (T3); a nested JWT is verified as a `Jwt` (R38, R60).
- N12 Key generation: api-absent:generate.
- N13 RFC 9278 thumbprint URIs, RFC 9864 fully-specified algorithm names and ML-DSA: additive later; `Ed25519` is `UnsupportedAlg` today (R65).

## Non-claim
- NC1 Zeroize of key material is best effort, through `base::SecretBytes` and the RustCrypto types' own `Drop`.
- NC2 Constant time is the RustCrypto crates' claim (hmac tag checks, aes-gcm, rsa, the curves), not measured here; a wasm engine's JIT sits outside every such claim. `rsa-decrypt` and `rsa-sign` carry the Marvin residual risk: rsa 0.10 is unaudited and its constant time rests on crypto-bigint (RUSTSEC-2023-0071); blinding uses the caller's entropy. Both are off by default for that reason, as the crate docs and `Cargo.toml` say.
- NC3 p256, p384, p521, ecdsa and rsa 0.10 have no independent audit; aes-gcm and aes have the 2020 NCC review.
- NC4 `finish` checks only the signature's length: a signature by the wrong key yields a token that fails verification downstream.
- NC5 A JWS `Payload` is authenticated bytes, not validated content.
- NC6 The timing of RFC 7516 11.4 is not measured (NC2); AES key-wrap failures return `Decrypt` without a substituted CEK, since a symmetric unwrap is no padding oracle.
- NC7 `Error` has no source chain by design: a cause would be an oracle (R53, R54), so `Error::source` is `None` and the kind is all a caller gets.
- NC8 An escaped secret JWK member (`d`, `p`, `q`, `dp`, `dq`, `qi`, `k`) is `Malformed` although RFC 8259 7 allows escapes: it is read borrowed so no unwiped copy of a secret is made; the public members accept them (R28): unit:jwk::decode::escaped_and_null_members.
- NC9 Distinctness of `apu` and `apv` (RFC 7518 4.6.2) is not checked on decrypt, and `encrypt` sets neither, so an ECDH-ES token this crate issues has both empty; a received pair is fed to the Concat KDF as given, which is sound whether or not they differ; spec:rfc7518#4.6.2.
